## 1. 方向与适用场景

### 1.1 最重要的事：方向

低代码有其明确的适用场景：**交互简单 && 轻逻辑**。典型场景包括：

- **海报**：0 逻辑 0 交互，非常适合
- **H5 运营活动页**：一次性页面，没有维护烦恼
- **表单收集页**：问卷调查等一次性场景
- **中后台页面**：CRUD 为主的管理系统
- **2D 游戏引擎**：如 Cocos Creator，低代码思想的经典应用

> **核心结论**：不要想着覆盖所有场景，挑一个垂直方向发力。方向越具体，自动化程度越高，平台也更好用。

### 1.2 次重要的事：简单

- **一旦复杂就不可视**，拖拽的优势就没有了
- 通常低码平台只实现了视图可视化，逻辑可视化很难（不如写代码直接）
- 适合逻辑可视化的场景：审批流、Scratch 等（前提是逻辑比较固定）

### 1.3 低代码的优缺点

**优点** ✅

- 本质是**提效**，以较少成本达到想要的结果
- 优势是**可视和快速**
- 能力源自于**物料（组件）的能力**

**缺点** ❌

- 上手成本较高
- 前端框架迭代快，低码平台需要跟着适配，维护成本大
- 不好维护和迭代、不好调试、不好定位问题
- 不好做性能优化
- 二次开发不可逆，很难做到持续可视化

## 2. 核心理念与架构概览

### 2.1 低代码的本质

低代码的核心本质在于**解耦**：将 UI 的描述（Description）与 UI 的实现（Implementation）分离开来。

- **UI 描述**：使用标准化的数据结构（Schema/DSL）来表达页面结构
- **UI 实现**：通过渲染引擎将描述映射为具体的运行时代码或 DOM

> **一句话总结**：低代码所有的操作都是在操作一个 JSON。

### 2.2 核心能力

- 抽象和建模
- 架构设计

### 2.3 平台四大组成模块

纵观大部分低码平台，主要由以下四部分组成：

```
┌─────────────────────────────────────────────────────────┐
│                      工具栏 (Toolbar)                    │
├──────────┬──────────────────────────────┬───────────────┤
│          │                              │               │
│  物料区   │         渲染器/画布区         │    设置器     │
│ (Materials)│        (Canvas/Renderer)    │   (Setters)   │
│          │                              │               │
└──────────┴──────────────────────────────┴───────────────┘
```

### 2.4 核心功能模块与沉淀产物

平台能力按功能模块划分，通常在 Engineering 中体现为 Monorepo Packages：

| 核心模块       | 功能描述       | 对应 SDK (Package)                    | 技术难点与职责                              |
| :------------- | :------------- | :------------------------------------ | :------------------------------------------ |
| **物料编排**   | 页面搭建与布局 | `layout-engine`                       | 4种布局引擎实现 (Flex/Grid/Canvas/Block)    |
| **物料渲染**   | Schema 转页面  | `material-renderer`                   | 递归渲染、增量更新、主题与多端适配          |
| **数据源管理** | 数据模型与连接 | `online-database`                     | **千万级数据渲染** (Canvas Table)、API 连接 |
| **流程引擎**   | 逻辑编排       | `flow-editor` <br> `flow-interpretor` | 流程编辑器（配置）与流程解释器（运行时）    |
| **资源中心**   | 静态资源管理   | `resource`                            | 大文件断点续传 (`file-uploader`)            |

**相关概念对照**：

- 物料编排 → 组件拖拽
- 物料渲染引擎 → 组件在页面中的布局渲染
- 数据源管理 → 数据表
- 流程编辑器(配置) + 流程引擎(执行) → 流程编辑
- 资源中心 → 静态资源管理

## 3. 协议与建模

### 3.1 协议的重要性

协议是低码平台的**基石**，贯穿整条链路：

- 扩展物料时，需要实现相应协议
- 物料拖到画布时，通过协议通信和解析
- 选中组件进行属性设置时，通过协议通信和解析
- 预览和发布代码时，通过协议生成代码

> **核心结论**：协议约定的好，事半功倍；约定不好，版版重构。协议本质上就是一堆 interface（固定格式）。

### 3.2 物料协议示例

```typescript
/** 单个物料约定 */
interface IComponent {
  /** 组件名 */
  componentName: string
  /** 组件中文名称 */
  title: string
  /** 缩略图 */
  icon?: string
  /** 包地址 */
  npm: {
    /** 源码组件名称 */
    componentName?: string
    /** 源码组件库名 */
    package: string
    /** 源码组件版本号 */
    version?: string
  }
  /** 分类：比如基础组件、容器组件、自定义组件 */
  group?: string
  /** 组件入参或者说是可配置参数 */
  props?: {
    name: string
    propType: string
    description: string
    defaultValue: any
  }[]
  /** 其他扩展协议 */
  [key: string]: any
}

// 举个例子
const componentList = [
  {
    componentName: 'Message',
    title: 'Message',
    icon: '',
    group: '基础组件',
    npm: {
      exportName: 'Message',
      package: '@alifd/next',
      version: '1.19.18',
      main: 'src/index.js',
      destructuring: true,
    },
    props: [
      {
        name: 'title',
        propType: 'string',
        description: '标题',
        defaultValue: '标题',
      },
    ],
  },
]
```

### 3.3 页面描述协议 (Schema)

Schema 是低代码平台的通用语言（DSL），通常采用 JSON 格式。整个平台编排完成之后，存储的数据一定是一个 JSON。

**Schema 关键要素**：

- **组件名称**：指定使用的物料类型
- **组件属性 (Props)**：配置组件的外观与行为
- **子节点 (Children)**：嵌套结构，形成组件树
- **事件绑定 (Events)**：DND 拖拽、Mouse Event 等交互逻辑
- **数据绑定 (Data Binding)**：连接数据模型与视图

### 3.4 数据模型优化

为了性能与维护性，采取**结构与数据分离**策略：

1. **框架结构 JSON**：描述页面的 DOM 结构与组件关系
2. **内容数据 JSON**：存储具体的业务数据

_渲染顺序：先渲染框架 JSON 生成骨架，再注入数据 JSON 内容。_

### 3.5 完整 Schema 示例

```javascript
const json = {
  version: '1.0.0', // 当前协议版本号
  componentList: [
    {
      componentName: 'Button',
      package: '@alifd/next',
      version: '1.0.0',
      destructuring: true,
    },
    {
      package: '@alifd/next',
      version: '1.3.2',
      componentName: 'Page',
      destructuring: true,
    },
  ],
  state: {
    // 全局状态
    name: '尤水就下',
  },
  componentsTree: {
    // 画布内容
    componentName: 'Page',
    props: {},
    children: [
      {
        componentName: 'Button',
        state: {},
        props: {
          type: 'primary',
          size: 'large',
          style: { color: 'red' },
          className: 'custom-button',
          onClick: {
            // 事件绑定
            type: 'JSFunction',
            value: 'function(e) { console.log(e.target.innerText) }',
          },
        },
      },
    ],
  },
}
```

## 4. 物料体系与插件化

### 4.1 物料的核心组成

物料最重要的两个东西：

- **数据协议**：JSON 数据
- **物料渲染引擎**

### 4.2 组件的分类

- **容器组件**：协助布局和嵌套
- **基本组件**：图片、文本、输入框、视频等
- **集成度较高的组件**：表格、表单、图表、自定义组件、业务组件

### 4.3 物料区实现

物料区会有一个 `componentList`，里面是各种组件的基本信息，直接循环渲染即可。同时会生成一个 `componentMap`，方便通过组件名快速获取组件元信息：

```javascript
const componentMap = {
  Message: {
    componentName: 'Message',
    title: 'Message',
    icon: '',
    group: '基础组件',
    // ...
  },
}

// 低码平台对外暴露加载和注册组件的方法
function createRegisterConfig() {
  const componentList = []
  const componentMap = {}
  return {
    componentList,
    componentMap,
    loadComponent: () => {},
    register: (comp) => {
      componentList.push(comp)
      componentMap[comp.componentName] = comp
    },
  }
}
```

### 4.4 组件加载方式

在前端加载文件只有两种方式：

**方式一：import()**

```javascript
const name = 'Button'
const component = await import('https://xxx.xxx/bundle.js')
Vue.component(name, component)
```

**方式二：script 标签**

```javascript
function loadjs(url) {
  return new Promise((resolve, reject) => {
    const script = document.createElement('script')
    script.src = url
    script.onload = resolve
    script.onerror = reject
  })
}
const name = 'Button'
await loadjs('https://xxx.xxx/bundle.js')
// 这种方式加载组件，会直接将组件挂载在全局变量 window 下
Vue.component(name, window[name])
```

### 4.5 插件化设计

物料管理的核心在于**插件化**，确保新增物料无需修改底座代码。

**前置概念**：

- 插件化基座
- 插件化协议
- 插件生命周期
- 插件开发

**组成**：数据协议 (JSON Schema) + 渲染实现 (Component Code)

**物料插件化的优点**：

1. **高扩展性**：新增物料无需修改底座代码，只需注册插件
2. **灵活加载**：支持本地与远程物料的无缝加载
3. **解耦性强**：物料与核心逻辑分离，维护成本低
4. **动态化**：支持按需加载，减少初始加载时间

### 4.6 如何扩展自定义组件

- **已有第三方组件**：需要简单适配（适配器模式），实现 `IComponent` 接口
- **待开发组件**：低码平台提供脚手架，基于固定模板开发
- **物料管理平台**：统一管理和操作组件，简单做法可以把 npm 当做物料平台用

> **建议**：尽量复用平台自身已有的组件库，我们不生产组件（或少生产），只是消费组件。

### 4.7 远程物料全生命周期

1. **构建**：物料协议、产物模块化规范
2. **发布**：上传至资源中心或 NPM
3. **加载 (Loading)**：
   - 配置获取：`fetch/xhr`、`SystemJs`、`modernJs`
   - 动态加载：`SystemJs`、`Module Federation`、`modern.js` 动态 import
   - 注册物料
   - 渲染：异步组件渲染物料
4. **优化**：
   - 缓存：LocalStorage / IndexedDB 避免重复加载
   - CDN：所有产物部署 CDN 加速
   - 版本管理：严格的版本控制解决兼容性问题

### 4.8 实际应用场景

1. **物料市场**：用户从市场中挑选需要的物料并动态加载
2. **动态表单**：表单控件作为物料插件化，通过配置加载不同控件
3. **动态布局**：根据用户需求，动态加载页面布局物料

## 5. 渲染引擎设计

### 5.1 核心工作原理

渲染器是 Schema 到 UI 的转换器，用来将 JSON 数据渲染成页面内容的组件。

**主要运行机制**：

1. **映射 (Map)**：Schema Type → 组件物料库代码
2. **递归 (Recursion)**：深度优先遍历树结构（Root → Leaf）
3. **策略模式 (Strategy)**：`Renderer` 负责数据加工 → 数据传递 → 组件渲染的全流程

**化简公式**：`UI = Transformer(componentTree)`

### 5.2 渲染器核心代码

```javascript
function renderNode(node) {
  if (!node) return null
  const component = components[node.componentName]
  const props = compute(node.props)
  const children = node.children.map((c) => renderNode(c))
  return React.render(component, props, children)
}
renderNode(componentTree)
```

### 5.3 数据驱动视图

低码平台秉持**数据驱动视图**的思想：

- 所有操作（拖拽、修改属性、调整位置）都是对 `componentTree` 这个数据进行修改
- 追加元素：往 `componentTree.children` 里 push 一个元素
- 修改属性：找到对应元素的数据修改其 props 值

> **核心结论**：画布编排的本质就是操作组件节点和属性。

### 5.4 全局数据管理

为了让每个组件都能直接获取到 `componentTree`，可以把它弄成全局的（放在 window、vuex、redux 上）：

- 每个模块共享同一份数据
- 平台暴露公共的修改方法
- 渲染器只负责根据数据渲染

### 5.5 画布区示例

```javascript
import ReactRenderer from '@alilc/lowcode-react-renderer'
import ReactDOM from 'react-dom'
import { Button } from '@alifd/next'

const componentTree = {
  componentName: 'Page',
  props: {},
  children: [
    {
      componentName: 'Button',
      props: {
        type: 'primary',
        size: 'large',
        style: { color: '#2077ff' },
        className: 'custom-button',
      },
      children: '确定',
    },
  ],
}

const components = { Button }

ReactDOM.render(
  <ReactRenderer componentTree={componentTree} components={components} />,
  document.getElementById('root')
)
```

**数组形式**（适合 H5 页面）：

```javascript
const componentTree = [
  { componentName: 'ElButton', height: 100, props: {}, style: {} },
  { componentName: 'ElInput', height: 300, props: {}, style: {} },
]
```

### 5.6 性能优化策略

- **增量更新 (OT)**：引入 Operational Transformation 算法，对比 JSON Patch，精准识别增、删、改、移
- **可视区渲染**：针对长列表或复杂画布，仅渲染 Viewport 内容

### 5.7 渲染器与出码

通常平台会提供 schema 渲染页面的功能，同时也可将所有配置输出 JSON Schema，我们称为**出码功能**。

## 6. 编排与布局引擎

### 6.1 布局引擎分类

| 引擎类型        | 描述                           | 应用场景             |
| :-------------- | :----------------------------- | :------------------- |
| **Flex 布局**   | 兼顾灵活与易用，类比 CSS Flex  | 管理后台、CRM、ERP   |
| **Grid 布局**   | 基于网格点坐标 (Grid Points)   | 仪表盘、可视化大屏   |
| **Block 布局**  | 自上而下的流式布局，灵活性较低 | 简单表单、OA、文档流 |
| **Canvas 布局** | 绝对定位，100% 自由灵活性      | 类设计软件、自由绘图 |

### 6.2 画布区实现方式

- **自由画布**：拖到哪里元素就放到哪里，配合容器组件可以协助布局实现自适应
- **流式布局**：组件从左到右从上往下自然排列，比如 H5 页面单纯从上往下平铺
- **自动布局**：拖哪放哪，但原来位置有组件会被挤开（递归挤开）
- **栅格画布**：类似前端组件库的栅格布局，一行 24 列 / 12 列
- **网格画布**：类似棋盘网格，每个网格 8px，拖拽时自动吸附到网格线
- **混合布局**：效率和通用性的权衡

### 6.3 编排引擎核心思路

- 基于拖拽的交互模型，实现所见即所得的页面设计
- 引入 flex 布局引擎，支持复杂布局的自动化排列
- 提供布局数据的实时更新与保存能力，便于回显与编辑

### 6.4 画布架构设计

编排引擎采用**微内核思想**，核心遵循 `f(state) -> view`，**组合层与渲染层彻底隔离**。

- render runtime(渲染引擎 sdk) + dsl(json) = 页面
- 事件：DND 拖拽、Mouse Event

## 7. 画布分层与交互

### 7.1 画布分层技术

借鉴浏览器渲染模型，使用冒泡机制穿透，利用 Event Bus 通信：

- **第一层 (渲染层)**：`div` 容器
  - **职责**：只负责页面渲染
  - **逻辑**：`render(dsl, document.querySelector("#root"))`
- **第二层 (交互层)**：覆盖在上面的 `div`
  - **职责**：处理右键菜单、辅助框选等交互事件
- **第三层 (事件层)**：最顶层 `div`
  - **职责**：捕获全局快捷键、全局手势
- **Event Bus**：所有层通过 event bus 进行通信

### 7.2 iframe 隔离

画布区本身也是个组件，可能受到父元素和全局的影响（如样式），导致和最终呈现页面有差异。

**解决方案**：把画布区搞成独立的 iframe，完美隔离，只不过增加了通信成本。

### 7.3 画布功能及扩展

**简单编排**：

- 物料均为块级，操作简便，不涉及复杂布局问题

**画布灵活编排**：

- 无限画布、引导线(栅格)、吸附对齐、旋转、快捷键、右键、缩放

### 7.4 高级交互实现细节

- **无限画布**：监听滚动事件，每次滚动动态给画布容器增加宽度/高度
- **辅助引导线**：使用 `div` 绘制（宽/高 1px），绝对定位，可拖动
- **智能吸附对齐**：
  - **算法**：计算邻近 DOM 节点，每个节点定义 **6个关键点**（四角+中心中点）和 **3条关键线**（横纵中轴）
  - **逻辑**：当拖拽距离 < 阈值时，自动吸附并将距离设为 0

### 7.5 撤销/重做 (Undo/Redo)

两种实现方式：

1. **快照模式**：每次操作时复制整个 `componentTree`，撤销和恢复直接重新赋值
2. **基于操作**：源数据只有一份，但有多个 actions。如 `add(comp)` 的反向操作是 `remove(comp)`

### 7.6 插件扩展点

插件不仅适用于顶部条：

- **物料区插件**：用脚手架扩展物料
- **画布区插件**：选中组件时扩展复制、删除、辅助线、上移下移等功能
- **设置区插件**：追加自定义表单项，如颜色选择器

## 8. 设置器/属性面板

### 8.1 设置器三种基本设置

- **Props**：组件属性
- **样式**：CSS 样式
- **事件**：交互逻辑

### 8.2 工作流程

1. 点选画布区的某个组件
2. 触发设置某个全局变量为当前组件
3. 右侧属性面板根据当前组件的 `componentName` 从 `componentMap` 中找到组件对应的 `setters`（可配置项）
4. 循环渲染 `setters`
5. 把当前组件的 state（初始值）赋值给 setters

> 这个过程和中后台应用的表单项（FormRender）是一样的。

### 8.3 配置面板解耦设计

对物料进行配置时，需要将**数据 (Model)**、**视图 (View)**、**操作 (Controller)** 分离。

- **中介者**：权限控制、数据转换 (Transformer)，暴露部分 API
- **预览**：`render(dsl: {type, key, props, animate, actions}, attrs:{}, children)`
- **提测、发布**

### 8.4 联动实现

字段 2 的显隐依赖于字段 1 的值，两种实现方式：

**方式一：发布订阅**

在字段 2 中监听（on）来自字段 1 的 emit 事件。缺点：依赖关系难以追踪。

**方式二：全局数据 + 模板表达式**

把字段都放在全局数据中，在字段 2 新增 `visible` 属性设置器，值为模板表达式：

```javascript
{{ globalData.field1 && ... && globalData.fieldN }}
```

因为数据是全局的，渲染时动态执行表达式确定是否渲染，跨组件或跨页面共享数据也变得轻而易举。

### 8.5 修改属性的数据流

修改属性设置区的表单项，实际上是去修改全局的 `componentTree`，然后画布区自动根据新的 `componentTree` 重新渲染。

> **单向数据流**：修改数据的入口只有一个，方便排查问题。

## 9. 事件脚本与安全

### 9.1 点击事件处理

**简单做法**：让用户自己写函数，运行时用 `eval` 或 `new Function` 执行。

**问题**：安全性、稳定性和效率不够。

### 9.2 两种限制方式

**方式一：暴露固定方法**

只接收参数，内置封装好的方法：

```javascript
// 平台内置
function jumpToPage(url) {
  window.open(url)
}

// 用户只需配置 url，并进行简单校验
```

**方式二：沙箱隔离**

让用户写脚本，但脚本具有良好的隔离性：

1. **with + new Function**：用 with 改变作用域实现隔离，用 try catch 捕获错误保障稳定性

```javascript
function parseExpression(str, self) {
  try {
    const code = `with($scope) { return ${str} }`
    return new Function('$scope', code)(self)
  } catch (err) {
    console.error('parseExpression.error', err)
    return undefined
  }
}
```

2. **iframe 沙箱**：在空的 iframe 里执行未知代码，最大程度实现隔离

```javascript
private executeCode(code: string, globalScope: InjectVmVarsType) {
  const sandbox = this.iframe.contentWindow
  sandbox.__INJECT_VARS = globalScope
  return sandbox.eval(`
    (() => {
      with (window.__INJECT_VARS) {
        return (${code})
      }
    })()
  `)
}
```

3. **等待新 API**：ShadowRealm

> **注意**：with + new Function 和 iframe 都可以通过原型链/parent 进行逃逸。

### 9.3 沙箱能拿到什么数据

主要看想暴露什么参数给组件：

- 全局数据
- 全局方法
- 父元素
- 当前组件的 state

直接传个包含以上数据的大对象给 with 即可。

## 10. 出码与发布

### 10.1 两种发布方式

**方式一：运行时渲染（同技术栈）**

开发一个 preview 页面，里面有固定的渲染器，加载对应组件库，远程获取页面的 json 数据传递给渲染器展示。

```javascript
import React, { memo } from 'react'
import ReactRenderer from '@alilc/lowcode-react-renderer'

const SamplePreview = memo(() => {
  return (
    <ReactRenderer
      className="lowcode-plugin-sample-preview-content"
      schema={schema}
      components={components}
    />
  )
})
```

**方式二：导出项目**

直接导出项目，可以二次开发或尝试 SSR 渲染（一旦二次开发基本不可逆）。

### 10.2 两种方式对比

| 维度     | 运行时渲染 (JIT) | 导出项目 (AOT)   |
| -------- | ---------------- | ---------------- |
| 编译时机 | 运行时编译       | 预编译           |
| 输出物   | JSON             | 项目代码         |
| 生效时间 | 实时生效         | 需打包重新发版   |
| 适用场景 | 一般场景够用     | 有性能要求用这个 |

**为什么运行时有性能问题**：渲染页面时需要将 json 进行一层转换，而导出项目是已经打包之后的代码。

### 10.3 术语说明

```javascript
// json：一个普通对象
// schema：一个有固定格式的普通对象
// json schema：一个描述 json 格式的普通对象
```

## 14. 常见问题与解答

### 14.1 模块之间如何解耦？

- 通过全局的发布订阅模式来通信
- 通过全局数据来共享，而不是直接相互传递数据
- 把每个模块都写成独立的项目，开发时自然强迫自己解耦
- 解耦最大的好处：重构或替换某个模块时，可以直接替换单个模块而不影响其他逻辑

### 14.2 除了全局变量，能在组件里维护自己的状态吗？

可以。新增一个 `state` 属性维护组件自身状态，并通过维护原型链层层向上获取父元素数据：

```javascript
state.__proto__ = parent.state
```

### 14.3 怎么支持跨平台？

低代码平台搭建后最终得到的是一个 json，本身就是以通用语言描述页面结构、表现和行为的，和平台无关。

要跨平台、跨框架，只需要做一个**适配层**去解析这些 json，导出成各平台、各框架需要的样子即可。

例如：vue 和 react 都有各自的 `createElement` 方法，到时候只需要把创建元素的方法换成各框架各自的方法就行。

> 思路简单，但每一种适配起来都很繁琐。

### 14.4 在哪里管理依赖？

低码平台一般有个**物料管理平台**，不仅管理组件，也管理项目依赖，最终表现为 json 中的 `packages` 字段：

```json
{
  "version": "1.0.0",
  "packages": [
    {
      "title": "fusion 组件库",
      "package": "@alifd/next",
      "version": "1.20.0",
      "urls": [
        "https://alifd.alicdn.com/npm/@alifd/next/1.20.0/next.min.js",
        "https://alifd.alicdn.com/npm/@alifd/next/1.20.0/next.min.css"
      ],
      "library": "Next" // 最终这样用：window.Next.componentName
    }
  ],
  "components": []
}
```

### 14.5 辅助线的实现（测距、对齐、吸附）

需要遍历所有物体拿到对应的 x、y 值。遍历较多组件时可以有策略：

- 是否在可视区
- 和目标元素的距离
- 超过十条或者 5ms 就停止遍历

### 14.6 版本维护

低码平台通常会有 version 字段来维护每个迭代，有多种 version：

- 协议有版本号
- 依赖有版本号
- 组件有版本号
- 每次发布也有版本号

### 14.7 怎么调用接口？

通常会有一个单独的模块来配置所有接口，然后在右侧的属性设置面板中挑选对应的接口即可。

### 14.8 如何监控和埋点？

接个监控和埋点库，在全局暴露方法，方便用户在右侧属性面板添加自定义事件。

### 14.9 多人开发同一个页面如何解决冲突？

两个人编辑同一个页面，先后点了保存该怎么处理？最终保存的只有 json 数据，问题转换为**怎么解决两个不同 json 的冲突**：

**方式一：借助 Git**

项目生成之初建 gitlab 仓库，借助 git 实现基于行的文本对比。

**方式二：自行实现对象合并策略**

把 json1 和 json2 的不同之处罗列出来，让用户保存时手动选择保留哪一个。

### 14.10 怎么调试？

- 前端：看控制台报错
- 非研发同学：低码平台需开发调试模块，形如 Vue/React 的 devtool 和 vConsole
- 最好将具体的错误和建议在页面上醒目展示

### 14.11 D2C && AI+

D2C 直接解析设计稿，经过繁琐转换后转成 json，然后生成页面。结合 AI 能够为其增色不少。

> 但这玩意几乎维护不下去，不过画饼需要😬
